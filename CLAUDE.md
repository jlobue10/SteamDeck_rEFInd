# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SteamDeck_rEFInd installs and configures the [rEFInd](https://www.rodsbooks.com/refind/) boot manager for dual/multi-booting a Steam Deck (SteamOS + Windows/Linux/Batocera/etc). It ships two ways to use it:

1. **Shell script installers** (bash, run on the Deck itself in desktop mode) that install rEFInd and drop a hand-authored `refind.conf`.
2. **A Qt/C++ GUI** (`GUI/src/`) that auto-detects the installed OSes/bootloaders on the EFI System Partition, generates `refind.conf` from that, and provides buttons for install/uninstall/systemd toggling. As of 2.0.0 the GUI also builds and runs on **Windows** (configure rEFInd from the Windows side of a dual-boot Deck).

There is no app backend. The privileged ESP work is compiled (`GUI/src/espops/` + the `SteamDeck_rEFInd_helper` binary) and has opt-in unit tests — `cmake -DBUILD_GUI_TESTS=ON` then `ctest`; four of the six suites run on Windows too. Everything else is still an installer/config-generator glued together with bash/PowerShell, so for the *installers* treat correctness as "does the resulting shell command / config stanza do the right thing on a real Steam Deck," not unit tests.

## Repo layout

- `SteamDeck_rEFInd_install.sh` — primary installer: pacman-based rEFInd install, EFI boot entry surgery via `efibootmgr`, copies `refind-GUI.conf` → `/esp/efi/refind/refind.conf`, installs the `bootnext-refind` systemd service.
- `refind_install_no_pacman.sh` — same end result, but downloads rEFInd from Sourceforge instead of using `pacman` (fallback when SteamOS pacman repos are broken).
- `install-GUI.sh` — installs the GUI app; the user-facing entry point is `curl -L .../raw/main/install-GUI.sh | sh` (the README's install command). It self-clones the repo into `$HOME/SteamDeck_rEFInd` (so it works piped from curl), disables `steamos-readonly`, stages files into `$HOME/.local/SteamDeck_rEFInd/`, pulls the latest GitHub release `.pkg.tar.zst` and installs it with `pacman -U`, re-enables `steamos-readonly`.
- `refind.conf` / `refind-GUI.conf` — the actual rEFInd config templates. Boot entries are **manually authored stanzas** (not rEFInd's auto-detection) specifically to control icon left-to-right order on the boot screen. `refind-GUI.conf` is the stripped/templated version the GUI overwrites with generated stanzas.
- `PKGBUILD` — Arch/`makepkg` package definition; builds the GUI via CMake and installs the binary, desktop file, icon, and both systemd unit files. This is the source of truth for the GUI's release artifact.
- `GUI/src/` — Qt Widgets C++ app. `mainwindow.cpp`/`.h`/`.ui` (config generator + button orchestration), `osdetect.*` (OS/bootloader detection, split `osdetect_common/linux/win.cpp`), `platform.cpp/.h` (the only `#ifdef Q_OS_WIN` site), and `rEFInd_GUI.manifest`/`.rc` (Windows UAC manifest). See architecture notes below.
- `Windows/GUI/` — the Windows Qt-build packaging (distinct from the top-level `Windows/` dual-boot-fix tooling): PowerShell equivalents of the Deck scripts, `assemble-deploy.sh`/`copydeps.sh`, the Inno Setup script `SteamDeck_rEFInd.iss`, and `SIGNING.md`. Nested under `Windows/` (not a lowercase `windows/`) to avoid a case collision on Windows filesystems.
- `scripts/` — the remaining bash helpers invoked by the GUI or systemd units: `zz_SteamDeck_rEFInd_install_config` (the sudoers rule template), `restore_EFI_entries.sh` (recreates missing SteamOS/rEFInd EFI entries), `pacman_install.sh`, `sourceforge_install.sh`, `scan_esp.sh` (the password-gated Deep Scan), and `uninstall_rEFInd.sh` (the automated Deck-side uninstall, see below). The privileged config/theme/randomizer scripts that used to live here — `install_config_from_GUI.sh` and its zenity fallback, both `_root.sh` helpers, `lib_esp_target.sh`, and both randomizers — are **gone**, replaced by the `SteamDeck_rEFInd_helper` binary (see the next bullet).
- **The privileged helper binary** (`GUI/src/helper/` + `GUI/src/espops/`; `NATIVE_HELPER_DESIGN.md` is the authoritative design). `espops` is a static library holding all ESP resolution, config/theme installation, and both randomizer payloads; it links into the GUI and into `SteamDeck_rEFInd_helper`, a QtCore-only console binary. `espops/` **and** `helper/main.cpp` are parity-locked byte-identical with the sibling rEFInd_GUI repo (which is the implementation lead); `espops/espconstants.h` is the one repo-owned file — it carries the product/data-dir names, the `/etc/SteamDeck_rEFInd` helper path, and this repo's Windows Scheduled-Task table, which has a `_bootnext` entry the sibling has no equivalent for. Subcommands: `install-config`, `install-themes`, `randomize-background`, `randomize-theme`, and on Windows `bootnext`, `migrate-tasks`, `enable-logon-task`/`disable-logon-task <subcommand>`. Exit codes are the contract the GUI keys its dialogs off (0 ok, 2 no/invalid invoking user, 3 no rEFInd ESP, 4 read-only target, 5 staging/space, 6 no source config/themes, 64 usage); the randomizers exit 0 on content/environment problems.
- **Passwordless Install Config / Install Themes:** the package installs the helper root-owned into `/etc/SteamDeck_rEFInd/` and a sudoers drop-in (`/etc/sudoers.d/zz_SteamDeck_rEFInd_install_config`, 0440, written only after `visudo -cf` passes — a broken sudoers.d file can lock sudo up) whitelisting the two **exact argument vectors** `… install-config` and `… install-themes`. Both live on the persistent /etc overlay so they survive SteamOS updates. The GUI runs `sudo -n` synchronously and shows the captured output; there is no zenity fallback any more (Install Config is passwordless-only, like Install Themes always was), and a missing rule or helper produces a "reinstall to repair" dialog. Root still never reads under the user's home: `espops/userio_linux.cpp` forks, drops to `SUDO_USER` (setgroups → setgid → setuid), and streams the files from the child — the fd-handoff equivalent of the old `runuser -u` reads, so a symlink/hardlink under `~/.local` still cannot exfiltrate root-readable files onto the ESP.
- **The four-script SHA-256 tamper hash-check is gone** — `matchesShippedScript()`, both `*ScriptTrusted()` functions, and the `resources.qrc` script embeds with it. Skew between the binary and the `/etc` copy is now caught by a **version handshake**: the GUI runs `helper --version` (no sudo needed) and compares against `APP_VERSION`. That is skew detection, not a security boundary — the boundary is root ownership of the helper, as it always was. The upside is that privileged logic can be fixed without blocking every user's Install Config as "modified"; the obligation is that the GUI and helper must be released together.
- `systemd/` — `bootnext-refind.service` (forces rEFInd to the front of the EFI boot order on every boot — SteamOS's A/B partition scheme can otherwise reorder/drop it), `rEFInd_bg_randomizer.service`, and `rEFInd_theme_randomizer.service`. All root units `ExecStart` **root-owned targets under `/etc/SteamDeck_rEFInd/`**, never the user-writable `~/.local` staging copies (a root unit running a user-writable script is a root escalation). Both randomizer units now run helper subcommands (`… /etc/SteamDeck_rEFInd/SteamDeck_rEFInd_helper randomize-background|randomize-theme`); `bootnext-refind.service` and `restore_EFI_entries.sh` deliberately stay bash — they do NVRAM writes, which the helper never does on Linux. `install-GUI.sh` and `PKGBUILD` install the helper binary and `restore_EFI_entries.sh`.
- `Windows/` — PowerShell/batch scripts run **from Windows**, not the Deck: fixing the "Windows boots straight past rEFInd" problem (`bootsequence-rEFInd-first.ps1`), a BIOS-update pre/post EFI-entry save-restore pair, and a background randomizer for the Windows side. All four elevated `.bat` entry points apply an admin-only ACL to `C:\rEFInd_Scripts` **by SID** (locale-independent) before registering scheduled tasks — the dir otherwise inherits an Authenticated-Users-modify ACE, and the scripts run `-RunLevel Highest`.
- `icons/`, `backgrounds/` — boot-menu assets (PNG only; backgrounds 1280x800, icons square — 128x128 matches rEFInd's default `big_icon_size`, and 256/512 variants ship for the GUI's larger Boot Icon Size choices) referenced by path from `refind.conf`.
- `themes/` — seven bundled upstream rEFInd themes (BlackCatMuzzle, Matrix-rEFInd, Starwars-rEFInd, rEFInd-fallout, rEFInd-glassy, rEFInd-mountain, wave, ~12 MB), each normalized so its directory name matches the `themes/<name>/...` paths inside its own `theme.conf` — the tree is copied verbatim to `EFI/refind/themes/`, so **don't rename theme dirs**. Upstream LICENSE/README/preview files are kept for attribution (credits table + takedown note in `README.md`; three themes have no published license; third-party content is committed as-is — don't fix its whitespace). Raw upstream clones (`themes/*-main/`, `themes/*-master/`) are gitignored working material — the normalized copies are the shipped ones. See the Themes section below.
- `qa/` — an on-Deck manual QA checklist (`DECK_QA_CHECKLIST.md`) plus driver script (`deck_qa_test.sh`), the only test-ish harness in the repo. It is pinned to a long-merged feature branch and predates the theme feature — treat it as a template for a new QA pass, not as CI.
- `VERSION` — plain version string (currently `3.2.1`), fetched by the update check and compared via `QVersionNumber`. Duplicated in: `GUI/src/mainwindow.cpp` (`APP_VERSION`), `GUI/src/CMakeLists.txt` (`project(... VERSION)`), `GUI/src/rEFInd_GUI.manifest` (four-part), `Windows/GUI/SteamDeck_rEFInd.iss` (`AppVersion`), and `PKGBUILD` (`pkgver`). **Keep all in sync when bumping.** The helper needs no separate version — `ESPOPS_APP_VERSION` is stamped from `project(VERSION)` and is what `helper --version` prints — but the GUI refuses to act on a mismatch (the handshake that replaced the tamper hash), so **the GUI and the helper must be released together**.

## Building the GUI

`GUI/src` builds three targets: the `espops` static library (all privileged ESP/config/theme/randomizer logic), the `SteamDeck_rEFInd` Widgets app, and `SteamDeck_rEFInd_helper` — a QtCore-only console binary linking `espops`, installed root-owned under `/etc/SteamDeck_rEFInd/` on Linux and shipped beside the GUI on Windows. `espops/` and `helper/main.cpp` are parity-locked byte-identical with the sibling rEFInd_GUI repo; port changes by copying the files and re-applying only `espops/espconstants.h`. **The pinned-Qt rule below applies to the helper exactly as it does to the GUI** — it links Qt too, so the build script and release workflow assert its symbol versions as well. On Windows the helper additionally needs `taskschd` on the link line (MinGW does not carry the Task Scheduler CLSID/IIDs in libuuid).

**The Linux build toolchain is pinned, and this matters more than it looks.** SteamOS 3.8.x ships qt6-base 6.9.1 and glibc 2.41 and is frozen there; Arch is rolling and is well past both. Qt symbol version nodes are *not* backward compatible, so a binary linked against newer Qt aborts in the dynamic linker on every Deck, before `main()`, with no GUI and no output when launched from a desktop entry:

```
libQt6Core.so.6: version `Qt_6.11' not found (required by .../SteamDeck_rEFInd)
```

This is exactly how 2.3.7 shipped broken: `.github/workflows/arch-release.yml` built in a plain `archlinux:base-devel` container and `pacman -Syu`'d into whatever Qt was current. Both the workflow and `scripts/build_GUI_pinned.sh` now pin an **Arch Linux Archive snapshot** (`2025/07/30`, bootstrapped from the `2025.07.01` tarball) whose qt6-base/glibc/gcc match SteamOS 3.8.16 exactly. Both also assert the built binary requires no Qt symbol newer than `Qt_6.9` and fail the build otherwise. **Only bump the snapshot when SteamOS itself moves to a newer Qt — keep the values in the workflow and the script in sync.**

Note that a full downgrade *into* the snapshot from a current image fails on package splits (`gcc-libs` → `libasan`/`libatomic`/…), which is why both paths start from an era-matched bootstrap tarball rather than downgrading. The tarball must be extracted under `podman unshare`/`sudo`; it carries root-owned files an unprivileged `tar` cannot write.

Reproducible local build (SteamOS has no compiler at all — `cmake`, `gcc`, `make`, `ninja` are all absent from the immutable rootfs, only `qmake6` exists):
```
scripts/build_GUI_pinned.sh          # podman; writes ./build-pinned/SteamDeck_rEFInd
```

Unpinned build (only correct if your Qt matches the target's):
```
cd GUI/src
mkdir -p build && cd build
cmake ..
make
```
Windows (MSYS2 UCRT64): `cmake -G Ninja -S GUI/src -B build-win && cmake --build build-win`, then `bash Windows/GUI/assemble-deploy.sh build-win/SteamDeck_rEFInd.exe deploy` and compile `Windows/GUI/SteamDeck_rEFInd.iss` with Inno Setup. The Windows exe embeds a `requireAdministrator` manifest (via `rEFInd_GUI.rc` for MinGW / a link flag for MSVC). Pushing a `v*` tag runs `.github/workflows/windows-release.yml` to build + SignPath-sign + release the installer (see `Windows/GUI/SIGNING.md`; no portable build is published — outside Program Files the app's privileged helpers would be user-writable).

Requires Qt5 or Qt6 (`Widgets`, `LinguistTools`) and a C++17 toolchain. No test suite; validate by building and exercising against a real or spare ESP. The official Linux release artifact is produced via `PKGBUILD` (`makepkg`).

## Architecture notes for `GUI/src`

As of 2.0.0 the GUI was refactored to match the sibling `rEFInd_GUI` repo (member state instead of file-scope globals; all external commands via `QProcess` argument lists / `QFile::copy`, never shell strings built from user input). Never reintroduce `system()`/`popen` with interpolated user data.

- **`OSDetector`** (`osdetect.*`): `osdetect_common.cpp` scans the ESP's `EFI/` vendor dirs for loaders (SteamOS `steamcl.efi`, Windows `bootmgfw.efi`, shim/GRUB/systemd-boot) and assembles cross-volume entries (SYSTEM labels, Batocera/Ventoy, removable ESPs by partition GUID). `osdetect_linux.cpp` enumerates via `lsblk -J` and finds the ESP — **`/esp` first** on the Deck. `osdetect_win.cpp` uses PowerShell + `mountvol`. The removable-ESP-by-partition-GUID path **fixes the old Windows-on-SD-card `volume` bug** that the README documents. As of the rEFInd_GUI 2.3.1 parity port, `detect()` iterates **every** ESP (not just one) and tags each entry with its ESP's partition GUID (`espVolumeId`), so generated stanzas boot regardless of which ESP rEFInd launched from; the Windows build also mounts **letterless non-system ESPs** on a temp directory via their `\\?\Volume{guid}` name (so a Linux ESP on an SD card is scanned from Windows), a bare systemd-boot vendor dir is named from the ESP's `loader/entries/*.conf` titles when os-release isn't readable, and scanned ESPs are guarded against duplicate cross-volume fallback entries. The four `osdetect` files are kept **byte-identical to the sibling rEFInd_GUI repo's** except for the Deck's `/esp` mountpoint in `isRunningSystemEsp()` (`osdetect_common.cpp`) — when pulling upstream detection fixes, copy the files and re-apply that one hunk. (`isLegionGo`/`isLegionGo2`/`isXboxAlly`/`nativePanelResolution` come along for the ride; the Deck fork's `mainwindow.cpp` keeps `resolution 3` — the right mode on every Deck — as the config default and only calls them via `effectivePanelResolution()` to seed the Res Override boxes.)
- **`Platform`** (`platform.cpp`, the only `#ifdef Q_OS_WIN`): data dir, installer launches (Linux = xterm + `scripts/*.sh`; Windows = `.ps1`), config/theme installs and unit/task toggles (Linux = `sudo -n` the helper + systemd incl. the Deck's `bootnext-refind.service`; Windows = in-process `espops` + Scheduled Tasks registered through the Task Scheduler COM API), `firmwareBootnumSupported()`, `preferWindowsAsDefault()` (SteamOS leads on the Deck, Windows on the Windows build), and the Pacman/Sourceforge (Linux) vs Sourceforge-only (Windows) install sources. The Sysd, Rand BG, and Theme Rand buttons work on BOTH platforms: on Linux they toggle the systemd units, on Windows the equivalent at-logon scheduled tasks, all three of which now run the helper exe directly (`SteamDeck_rEFInd_bootnext` → `helper bootnext`, which writes UEFI BootNext to the rEFInd entry and supersedes the legacy "rEFInd Boot Sequence" bcdedit task from the Dual Boot Fix zip; `…_bg_randomizer`; `…_theme_randomizer`). Registration is `EspOps::setLogonTask()` via COM rather than `schtasks`, because the handheld-critical battery settings (`AllowStartIfOnBatteries`, `DontStopIfGoingOnBatteries`) cannot be expressed on the schtasks command line. The Inno installer offers an unchecked-by-default checkbox that runs `helper enable-logon-task bootnext`, runs `helper migrate-tasks` on every install so tasks left by an older version stop pointing at removed `.ps1` wrappers, and `[UninstallRun]` unregisters all task names — current and legacy — with `schtasks` (deleting needs no battery settings). The old `systemdFeaturesAvailable()` gate was removed with this change. `installConfig()` and `installThemes()` both run synchronously and are passwordless-only — Linux via `sudo -n` on the helper (readiness probed with `sudo -n -l` plus the `helper --version` handshake), Windows in-process since the GUI is already elevated. Their output is captured and `MainWindow` presents the success/failure dialog from it; don't regress either back to a fire-and-forget launch. The zenity fallback and `installConfigShowsOwnDialogs()` are gone with the scripts. All Windows launches of PowerShell (here and in `osdetect_win.cpp`) go through `Platform::windowsSystemExecutable()` — absolute `%SystemRoot%\System32\...` paths, never PATH lookup — and every `runPowerShell()` command is prefixed with `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8;` (PS 5.1 emits redirected output in the OEM codepage; a localized volume label once produced invalid-UTF-8 JSON and detection found no OS at all — don't drop the prologue).
- **`MainWindow`**: detection populates the four boot-option combos (`BootEntry` via `QVariant`); `applyAutoSelection()` + `compactBootSelections()` pack detected OSes into slots 1, 2, … with no gaps, and the **Rescan** button re-detects and resets to defaults. `createBootStanza()` renders one data-driven stanza per non-None slot (stanza order = on-screen icon order). The optional "Include all OSes" checkbox (`IncludeExtraEntries` in the INI, off by default) appends stanzas for every *detected* entry not already slotted — after the slotted ones, with stock rEFInd icons (`stockIconFor`) — for outlier machines with more valid bootloaders than slots; slot curation stays authoritative when it is off. **Res Override**: a checkbox + width/height boxes (main grid row 10) force `resolution <W> <H>` in the generated config when armed with two positive values (`resolutionOverride()`); unchecked — the default, never auto-enabled — keeps `resolution 3`. Stored as `[Resolution]` `ResOverrideEnabled`/`ResOverrideWidth`/`ResOverrideHeight` in the INI; the boxes are seeded once (only when the INI holds nothing) from `effectivePanelResolution()` (quirk table, else EDID — note both Deck panels honestly report portrait 800x1280), computed on the detection worker thread (`panelPrefill`) because the probes spawn PowerShell on Windows. Settings persist **by text** (`BootOption0XText`) in `~/.local/SteamDeck_rEFInd/GUI/rEFInd_GUI.ini`; everything except the boot-option selections restores in the constructor (`readEarlySettings()`) and persists the moment a control changes (`initSettingsPersistence()`) — the destructor's `writeSettings()` is only a final snapshot, because force-termination (overlay / task switcher, suspend) skips destructors. Boot-option selections restore in `readSettings()` once the scan delivers combo contents and persist on change only after that (`settingsLoaded` gates both; `populating` masks programmatic rebuilds). Create Config stages all five PNGs (`copyPng` — chunked `QFile`→`QSaveFile` copy) and the theme conf first, then writes `refind.conf` last via `QSaveFile` with `setDirectWriteFallback(false)` — any staging failure keeps the previous config. `steamFirmwareBootNum()` matches the SteamOS firmware entry from `efibootmgr -v` by loader device path + partition (BootOrder-preferred), with the exact label only as a fallback — not the old `.*steam` label regex.
- The `Firmware_bootnum` option (SteamOS) still needs an existing SteamOS EFI entry at config-generation time (queried via `efibootmgr`); it keeps the SteamOS icon visible during the rEFInd→SteamOS handoff. Linux only.
- Keep the split: GUI builds config + orchestrates; the bash/PowerShell scripts do anything needing elevation.

## Themes and the boot-screen preview

- **Theme selection** (since 3.2.0): `Theme_comboBox` (main grid row 13, above the Language row, with `Theme_Rand_On/Off_pushButton` and `Install_Themes_pushButton`) offers None (empty item data), one entry per `<dataDir>/themes/<name>/theme.conf` dir (dir name = display text = item data, **never translated** — like BootEntry names), and Random (item data `*random*` — note the sibling rEFInd_GUI repo uses `__random__`; the sentinels differ). Persisted as `[ComboBoxes] ThemeSelection` = item data (sibling uses `Theme`). `populateThemeCombo()` re-runs on `LanguageChange` so `tr("None")`/`tr("Random")` retranslate; the selection survives because it's keyed by data. `themesRootDir()` prefers `<dataDir>/themes`, falling back to a `themes/` beside the binary.
- **Config generation**: a non-None selection makes `generateConfigText()` append `include themes/active_theme.conf` as the final directive — the include target never varies, switching themes replaces one file. rEFInd applies the last occurrence of a setting, so the theme deliberately supersedes the generated `banner`/`big_icon_size`/`resolution` above it (`hideui` ORs across files — a theme can only hide *more*), and rEFInd ignores a missing include, so the config stays bootable before Install Themes has ever run. Per-stanza `icon` lines still point at the user-picked `os_iconN.png`. `resolveThemeChoice()` resolves Random to a concrete theme at Create-Config time (logged) and `stageActiveThemeConf()` copies its theme.conf → `<dataDir>/GUI/active_theme.conf` via QSaveFile; None removes the staged copy (so Install Config stops publishing a stale one); a staging failure aborts before `refind.conf` is written (publish-last).
- **Install Themes** copies the theme trees to `EFI/refind/themes/<name>/`. It is passwordless-only, like Install Config now is: `sudo -n /etc/SteamDeck_rEFInd/SteamDeck_rEFInd_helper install-themes` (an exact-argument NOPASSWD line). The invoking user comes from `SUDO_USER` at runtime, and root never reads `~/.local`: `espops/userio_linux.cpp` forks, drops privileges (setgroups → setgid → setuid), enumerates and streams the trees from the child, and the parent writes them — replacing the old `tar | tar --no-same-owner` pipe while keeping its guarantees (symlinks refused — vfat can't hold them anyway; no `..`/absolute members, so extraction can't escape). Free-space precheck, per-theme staged directory swap with `.old-` rollback, distinct exit codes (2 no sudo user, 3 no rEFInd ESP, 4 read-only target, 5 staging/space, 6 no themes). Windows runs the same `espops/themesinstall.cpp` in-process from the already-elevated GUI. The **Install Config** path additionally publishes the optional staged `active_theme.conf` into the ESP's `themes/` subdir before `refind.conf` — all three config installers share the `dest_dir_for()` pattern.
- **Theme randomizer** (`helper randomize-theme`, driven by `systemd/rEFInd_theme_randomizer.service` on Linux and the at-logon `SteamDeck_rEFInd_theme_randomizer` task on Windows, toggled by the Theme Rand buttons via `Platform::setThemeRandomizer()` — see the Platform bullet above). On each boot (or Windows logon) it copies a random *installed* theme's theme.conf over the ESP's `themes/active_theme.conf`, but **exits 0 silently unless `refind.conf` actually contains the include line** (theming off is the normal state). It takes no user-writable input at all — candidates come from the ESP's own root-owned `themes/*/theme.conf` (no `runuser`, no sed placeholders). If both randomizers are enabled, the theme's `banner` wins over the randomized background.
- **Boot-screen preview** (`PreviewDialog`, `GUI/src/previewdialog.cpp/.h`, predates 3.0.0): the Preview button renders a mock 1280x800 boot screen (rEFInd's reference geometry — background fillscreen, one centered row of entry icons sized/spaced like rEFInd's but shrunk so every entry stays visible where rEFInd would scroll, selection backdrop behind the default entry, rounded name-initial tiles for missing icons) plus a second tab with the generated `refind.conf` text (tab title deliberately untranslated — it's a filename). `PreviewTheme` (kept **byte-identical to the sibling rEFInd_GUI repo's**) is the only theme.conf parser in the codebase: it reads exactly `banner`, `selection_big`, `big_icon_size`, and `hideui` (only the `label` token; `hideui` accumulates across repeated lines like rEFInd's own config.c, and `label` suppresses the mock's entry names). `resolveThemeAsset()` re-roots any `themes/...` path onto the local themes dir and returns nothing for a dangling path, falling back to the themeless drawing for that element. Random previews a concrete random pick, with a note that Create Config re-picks.
- **Distribution**: all five rEFInd install paths (the four bash installers + `Windows/GUI/install_rEFInd.ps1`) copy `themes/` onto the ESP best-effort at install time (warn-and-continue — themes are only consulted when the config includes `active_theme.conf`); keep the step in sync across all five like the UEFI driver downloads. `install-GUI.sh` stages `themes/` to `~/.local/SteamDeck_rEFInd/themes/`; `Windows/GUI/assemble-deploy.sh` ships `themes/` in `deploy/` (the Inno installer picks it up via `recursesubdirs`) and `Platform::prepareDataDir()` seeds it into `%LOCALAPPDATA%` via `copySeedDir()` — merge-add-new, never overwrites existing user files. Users may hand-edit or add themes under the staged dir (any folder with a `theme.conf` counts — documented in README) and re-run Install Themes. `scripts/uninstall_rEFInd.sh`'s unit loop disables all three services (bootnext, bg, theme); ESP theme files fall with `EFI/refind`.

## Internationalization (GUI)

The GUI is translated via Qt Linguist files: `GUI/src/SteamDeck_rEFInd_{en_US,ar,bn,de,es,fa,fr,hi,id,it,ja,ko,pt,ru,scn,tr,uk,ur,vi,zh_CN}.ts`, listed in `TS_FILES` in `CMakeLists.txt`. On Qt 6, `qt_add_translations()` compiles them at build time and embeds the `.qm` under `:/i18n`, where `main.cpp` loads them with the locale-fallback `QTranslator::load(QLocale(), ...)` overload (plus a `qtbase` translator for Qt's own dialog strings); on Qt 5 the `.qm` are only generated into `translations/` next to the binary. Rules: wrap every new user-facing GUI string in `tr()` (in `Platform`, use `QCoreApplication::translate("Platform", ...)`); after changing strings, refresh **all** `.ts` files with `lupdate` (or the `update_translations` target) so translators see the new entries — unfinished entries just fall back to English. Exception: `lupdate` refuses the Sicilian file ("target language is not recognized" — Qt has no `scn` locale) and silently leaves it untouched, so new `<message>` entries must be added to `*_scn.ts` by hand (lrelease compiles it fine); the same applies in the sibling rEFInd_GUI repo. Do NOT translate `BootEntry` display/menu names ("Windows", "SteamOS", "Ventoy", ...): they are matching identifiers persisted by text and produced by the parity-locked `osdetect_*` files. `.ui` strings that are overwritten at runtime are marked `notr="true"` — keep doing that for new ones. The en_US file is the source-language reference and stays untranslated. The `QT_LAYOUT_DIRECTION` message (anchored in `main.cpp`) must stay `RTL` in the ar/fa/ur files — it is what mirrors the layout for right-to-left languages. The remaining shell/PowerShell scripts and the helper binary's output are deliberately English-only (the helper's messages are shown verbatim in GUI dialogs, and `espops` is parity-locked, so localizing it is a both-repos change) — see `I18N_AUDIT.md` before localizing them. Runtime language selection lives in `uitranslation.cpp` (`UiTranslation::apply`, saved as `Language/UiLanguage` in the INI; the Language combo switches live via `changeEvent`/`retranslateUi` + `applyDynamicTexts()` — put any new code-set string in `applyDynamicTexts()` so a language switch refreshes it). Qt 6 builds also embed the matching `qtbase_*.qm` from the build machine under `:/i18n_qtbase` (SteamOS ships no qt6-translations package); `UiTranslation` falls back to them last. Detection runs on a worker thread (`startDetection()`; don't call `detector.detect()` on the GUI thread) and the update check uses `QNetworkAccessManager` (Qt Network) — both UI freezes were deliberate removals; don't reintroduce synchronous variants. The GUI appends diagnostics to `<dataDir>/GUI/logs/` (English on purpose), and boot selections persist by stable key (`BootOption0XKey` = volume|loaderPath) with the old text keys as fallback. Optional unit tests: `cmake -DBUILD_GUI_TESTS=ON` + ctest (`GUI/src/tests/`, links the parity-locked osdetect files untouched).

## Working with `refind.conf`

- Boot stanza order in the file is the left-to-right icon order on screen — this is deliberate (see repo layout note above); don't "clean up" the file into auto-detect mode.
- SD-card/USB Windows entries need a `volume <partition GUID>` line pointing at that device's ESP. As of 2.0.0 the detection engine resolves this automatically (the old README-documented broken path), so manual edits are no longer required when the media is inserted at Create-Config time.
- Icon/background filenames referenced in `refind.conf` must match actual files shipped in `icons/`/`backgrounds/` (or the GUI's staged copies under `~/.local/SteamDeck_rEFInd/`). The hand-authored config's banner is `backgrounds/background.png` (since v3.1.2) — an ESP-relative `themes/` path now means the bundled theme trees, nothing else.
- Generated stanza `icon`/`loader` path lines must stay **unquoted** — rEFInd does not strip quotes from those tokens, and v3.1.2's quoting made every generated stanza unbootable (fixed in v3.1.3). `menuentry` titles and `volume` labels stay quoted, and the title sanitization (stripping quotes/braces/newlines so a crafted systemd-boot title can't inject a stanza) is retained.

## Conventions to follow when editing scripts

- Every privileged install/uninstall script brackets its `pacman`/file-copy work with the shared `disable_readonly`/`enable_readonly`/`restore_readonly_on_exit` harness (EXIT trap; distinct exit 70 when even the restore fails; both helpers are no-ops when `steamos-readonly` doesn't exist — Bazzite/ChimeraOS) — preserve that bracketing in any new script that writes outside `$HOME`.
- **What survives a SteamOS update:** `/home` is its own partition (so everything under `$HOME/.local/SteamDeck_rEFInd/` persists), and `/etc` is an overlay with its upperdir on `/var`. `/usr` is the immutable A/B rootfs and is *replaced wholesale* by an update — which takes `/usr/bin/SteamDeck_rEFInd` and the pacman package registration with it. That is why `install-GUI.sh` copies the binary out of `/usr/bin` into `$HOME/.local/...` and points the desktop entry at the copy; the GUI keeps working after an update even though the package is gone. Don't "simplify" the desktop entry to exec `/usr/bin/SteamDeck_rEFInd`. Re-running the installer is what restores the package and the `/etc` units. Re-running `install-GUI.sh` no longer resets saved settings: `GUI/*` staging is file-by-file, and `rEFInd_GUI.ini`/`refind.conf`/`background.png`/`os_icon?.png` are only copied when absent. It also writes root-owned `/etc/SteamDeck_rEFInd/background-dir` (the bg randomizer's pointer to the user's backgrounds dir — validated, read as **data** via fd redirection, never sourced), and checks out the release tag *before* disabling readonly so the staged scripts hash-match the released binary.
- **Desktop entries:** install to `$HOME/.local/share/applications/` (an authorized XDG location) and make `~/Desktop/` a *symlink* to that. KDE only treats a `.desktop` file as a launcher when it resolves into an authorized applications dir; an executable copy dropped straight into `~/Desktop` gets run through the shell instead, which fails on `line 1: [Desktop: command not found`. Setting `metadata::trusted` does not help here — that is GNOME's mechanism, and `gio` refuses it on SteamOS anyway.
- **Writing into an existing rEFInd install goes through `espops/espresolve_*.cpp`** (`EspResolver::resolve()`), never a hardcoded `/esp/efi/refind/`. It returns the ESP that actually boots rEFInd: the one the firmware's rEFInd entry points at (verified to still contain `EFI/refind/refind*.efi`, so a stale NVRAM entry can't shadow the live install), else any ESP containing rEFInd, else the running system's ESP (`/esp` first on the Deck). This replaced the old `scripts/lib_esp_target.sh` + `Get-RefindNvramEsp` pair, so there is no longer a bash↔PowerShell parity burden here — one C++ implementation serves both platforms, and `espops/loadoption.cpp` is the single `EFI_LOAD_OPTION` parser. It needs root on Linux (ESPs are mounted `0700 root:root`), which is why it lives behind the sudo-gated helper. Its probe mounts are `ro,nosuid,nodev,noexec` on private temp dirs, unmounted by the resolver's destructor (so keep it alive until every write is finished and synced); `makeWritable()` remounts rw only the chosen target and only when it's one of the resolver's own probe mounts. The *install* scripts legitimately still target `/esp` — they install rEFInd onto the running system's ESP, which is the intent there. Without this, a rEFInd installed from Windows or onto an SD card keeps receiving config updates at a path the firmware never boots, whose symptom is "I changed the config and nothing changed at boot".
- The randomizer units are cosmetic boot-time services: content/environment problems warn to stderr and **exit 0** — nonzero is reserved for internal errors (a red failed unit for a missing background would be worse than the symptom). `helper randomize-background` enumerates the user's backgrounds in the invoking user's context (fork + privilege drop, with a wall-clock timeout) and caps content with an in-stream size limit — no PAM stack, no `head -c` pipe, no `ulimit -f` (RLIMIT_FSIZE never reliably survived `runuser`'s PAM stack anyway) — publishing via root-private staging + rename. It reads the backgrounds directory from the root-owned `/etc/SteamDeck_rEFInd/background-dir` pointer as data, never sourcing it. The theme randomizer copies these semantics but takes no user input at all (see the Themes section).
- The staged ESP config install (`espops/configinstall.cpp`) is **staged, publish-last — not atomic** (FAT32 has no rename atomicity): every file lands as `.<name>.new.<suffix>` in its destination dir first, a stale-staging sweep runs right after the destination is ensured (traps can't survive SIGKILL/power loss), and the publish loop writes `refind.conf` last. Publishing goes through `EspOps::publishRename` because on Windows both `QFile::rename` and UCRT's `std::rename` refuse to overwrite an existing file (it uses `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` there), and staging objects must be destructed before the rename — `QTemporaryFile` keeps its native handle open after `close()`, and Windows cannot rename an open file. After publishing, a `refind.conf.origin` sidecar records who installed the live config (product/platform/version/sha256/timestamp), and each install notes in its output when it is replacing another GUI's install or a hand-edited config — the ESP's one live config is shared by this product's Deck and Windows builds (and by the sibling rEFInd_GUI), and alternating installs from two GUIs otherwise silently undo each other's changes while both report success (the 2026-08 "Install Config succeeds but nothing changes at boot" report, closed in `qa/INSTALL_CONFIG_DEBUG_RUNBOOK.md` §10). Best-effort and informational only. Relatedly, Create Config writes `refind.conf` without `QIODevice::Text` so both platforms stage identical bytes.
- **Never toggle an entry's active state with a bare `efibootmgr -a`/`-A`.** SteamOS 3.9's stack (efibootmgr 18-3 / efivar 39 / valve kernel 6.16) cannot rewrite an *existing* `Boot####` variable in place — the toggle fails even as root, while `-c` (create), `-B` (delete), and `-n` (BootNext, normally a new variable) keep working. Every script that toggles active state must (1) skip the write when the entry is already in the requested state (read the `*` from `efibootmgr` output), and (2) on failure retry after `chmod 666` on `/sys/firmware/efi/efivars/Boot####-8be4df61-93ca-11d2-aa0d-00e098032b8c`, restoring 0644 immediately after (empirically verified on real hardware). See `toggle_entry_active()` in the four installers, `activate_entry()` in `scripts/restore_EFI_entries.sh` and `scripts/uninstall_rEFInd.sh` — keep them in sync. The unguarded variant is what made `bootnext-refind.service` fail on every boot with healthy NVRAM (issue #215) and aborted GUI installs at 90% (the `systemctl enable --now bootnext-refind.service` lines are now guarded with `||` warnings for the same reason).
- EFI boot-entry manipulation always goes through `efibootmgr`, extracting boot numbers with `sed -nE 's/^Boot([0-9A-Fa-f]{4})\*? +<label>.../\1/p'` — never `$`-anchor a bare label, because efibootmgr ≥ 18 appends a tab + device path after the label even without `-v` (anchored matches silently never match). The install scripts delete refind-install's exact-label "rEFInd Boot Manager" entry up front, then **create the new `rEFInd` entry before deleting old ones** (identified as the head of BootOrder, which `efibootmgr -c` sets) so a failed create can't leave the Deck with no rEFInd entry, and end with a verification summary read back from live NVRAM (plus zenity dialogs in the GUI-invoked pair). This mirrors rEFInd_GUI's install scripts — keep the pattern in sync across `scripts/pacman_install.sh`, `scripts/sourceforge_install.sh`, `SteamDeck_rEFInd_install.sh`, `refind_install_no_pacman.sh`, and `scripts/restore_EFI_entries.sh`.
- Scripts resolve the ESP's disk and partition number from the `/esp` mount (findmnt + sysfs fallback for empty `lsblk PKNAME`); the `scripts/` installers **fail closed** — refuse to touch NVRAM — when resolution fails, because the historical `/dev/nvme0n1` partition 1 fallback created broken entries on 64GB Decks that boot from eMMC (`/dev/mmcblk0`). The legacy top-level installers (`SteamDeck_rEFInd_install.sh`, `refind_install_no_pacman.sh`) fail closed too, re-enabling `steamos-readonly` at that exit; they do not (yet) use the full EXIT-trap/`set -e` harness. The `scripts/` installers also wrap the whole install in an EXIT trap that restores `steamos-readonly` after any failure (distinct exit 70 when even the restore fails) and run under `set -e` — new commands whose failure is tolerable must be explicitly guarded (`|| true`, `if`, or `|| echo` warnings).
- **systemd automounts** (since 2.6.1): SteamOS 3.9 mounts `/esp` and `/efi` through `esp.automount`/`efi.automount`. Two consequences for every script and for the GUI: (1) until a path resolves *through* the mount point, the vfat mount doesn't exist — a plain `stat()` of the mount point does NOT trigger the automount (`AT_NO_AUTOMOUNT` since Linux 4.14), but stat'ing `<point>/.` does, even without permission on the root-only mounted fs; the GUI (`listPartitions()`/`espDeepScanUseful()`) and `scripts/scan_esp.sh`/`scripts/uninstall_rEFInd.sh` poke `/esp/.` etc. first, `detect()` additionally recovers a completely unmounted ESP's entries from the deep-scan cache / `efibootmgr` by partition GUID, and `scan_esp.sh`'s root payload temp-mounts unmounted ESPs read-only. (2) findmnt lists the `autofs` row (SOURCE `systemd-1`) **before** the real vfat row, so `findmnt -no SOURCE /esp | head -1` returns `systemd-1` — use `grep -m1 '^/dev/'` for SOURCE and `tail -1` for FSTYPE (all install/uninstall/restore scripts do); `findmnt -S <dev>` (as in `lib_esp_target.sh`) is immune.
- All five rEFInd install scripts (the four above plus `Windows/GUI/install_rEFInd.ps1`) download the Xbox 360 controller UEFI driver (`UsbXbox360Dxe.efi`) into the ESP's `EFI/refind/drivers_x64/` so docked/wired Xbox-style gamepads work in the boot menu; the URL temporarily points at the jlobue10 fork of the SkorionOS driver (Legion Go 2 PIDs + Ally poll-timeout fix + v1.7.3's right-stick-in-Mouse-mode fix) — revert it to SkorionOS once upstream PR #7 — which supersedes the old PIDs-only PR #6 and carries the full fork state — is merged and released upstream, and keep the step (and the eventual URL revert) in sync across all five. The scripts fetch the standard release `UsbXbox360Dxe.efi` — the correct default; `UsbXbox360Dxe-debug.efi` is troubleshooting-only.
- The same five scripts also download the [`TouchI2cDxe.efi`](https://github.com/jlobue10/TouchI2cDxe) touchscreen UEFI driver into `drivers_x64/`, on **both Deck models** — DMI product_name `Galileo` (OLED) or `Jupiter` (LCD, supported since driver v1.2.0); read from `/sys/class/dmi/id/product_name` in bash, `Win32_ComputerSystemProduct.Name` in the ps1, where the extra download is a numbered `Write-Step` making `$TotalSteps` 7 on a Deck and 6 elsewhere. Both touch panels are HID-over-I2C (FocalTech FTS3528, same I2C constants on both models; only the panel reset GPIO differs, which the driver resolves itself via SMBIOS), structurally invisible to USB drivers; TouchI2cDxe produces `EFI_ABSOLUTE_POINTER_PROTOCOL` (rEFInd consumes it natively) and rotates the portrait touch matrix onto rEFInd's landscape GOP mode. Same rules as the controller driver: version-agnostic `releases/latest` URL, download failure warns and continues, no config file needed, removed with `EFI/refind` on uninstall. Keep the step in sync across all five scripts (the sibling rEFInd_GUI repo gates its equivalent block on Ally `RC73XA*`/`RC73YA*` boards, Galileo/Jupiter, **or** the ASUS Zenbook Pro 14 Duo `UX8402VV*`, and also cleans up the superseded `AllyTouchI2cDxe.efi` — this repo never shipped that file, so its scripts skip the cleanup).
- `Windows/GUI/install_rEFInd.ps1` and `uninstall_rEFInd.ps1` — the only privileged `.ps1` files left, both standalone terminal tooling rather than GUI helpers — are kept identical to the sibling rEFInd_GUI repo's `windows/` versions except `rEFInd_GUI` → `SteamDeck_rEFInd` and `"rEFInd GUI"` → `"SteamDeck rEFInd GUI"` — port upstream changes by copying + renaming — **and this repo's installer deliberately omits rEFInd_GUI's Secure Boot check/warning block** (`Confirm-SecureBootUEFI` + sbctl note; not applicable to Steam Deck) — don't re-add it when porting. As of the 2.3.1 parity port the installer writes a dedicated `rEFInd` **Boot#### EFI variable directly** (`SetFirmwareEnvironmentVariableW`; bcdedit cannot create firmware entries on current Windows 11, and repointing `{bootmgr}` drags Windows' optional-data blob into the entry — rEFInd_GUI issue #23), restores a `{bootmgr}` repointed by older versions, never touches entries carrying the `"WINDOWS"` blob (hex `57494e444f5753`), and verifies via NVRAM read-back; the config installer and randomizers target the ESP the firmware rEFInd entry actually points at through `espops/espresolve_win.cpp` — direct `Boot####` variable reads (`GetFirmwareEnvironmentVariableW`, locale-independent, replacing the old `bcdedit /enum firmware` + `QueryDosDevice` parsing; it needs `SeSystemEnvironmentPrivilege` enabled first or every read silently returns empty), BootOrder first then the conventional `Boot0000`–`Boot00FF` range (so an entry dropped from BootOrder is still found), matching by GPT hard-drive node + `\EFI\refind\refind*.efi` loader path — before falling back to a filesystem scan. Extend ESP discovery in `espops`, not in the callers; `uefi_refind.ps1` and its bash twin are gone. The two surviving `.ps1` files keep their own private copies of the NVRAM helper block (they run standalone, without the binary) — that duplication is deliberate, and `espops/espresolve_*` is now its parity partner. `uninstall_rEFInd.ps1` reverses everything and is run elevated by the Inno uninstaller (`[UninstallRun]`+`Verb: runas` after a yes/no prompt; `[UninstallDelete]` scrubs the per-user data dir; the app itself lives under Program Files). `scripts/uninstall_rEFInd.sh` is the Deck-side counterpart (disables `bootnext-refind` FIRST — it recreates the boot entry every boot — then entries/Windows re-activation/ESP files/refind package; `--keep-esp-files`, `--remove-app`; its unit loop also disables both randomizer services, it removes the desktop entry, and a failed `pacman -R refind` is a warning, not an abort); keep the pair in behavioral parity. `install_rEFInd.ps1` stages downloads in `%SystemRoot%\Temp\SteamDeck_rEFInd-Staging-<guid>` with an admin-only DACL applied via `Set-Acl` (works under both PS 5.1 and pwsh; `C:\ProgramData` was squattable through Users create-subfolder + CREATOR OWNER), refuses a pre-existing GUID dir or reparse point, sanity-checks downloads by magic bytes (`Test-FileSignature` — deliberately *not* Authenticode; rEFInd binaries are unsigned), and publishes via `Publish-FileAtomically` (staged same-directory swap — short replace window, not zero). `uninstall_rEFInd.ps1`'s `Set-BootOrderIds` refuses to write an empty BootOrder (`Set-UefiVar` treats zero length as delete, which would remove the variable itself) and rebuilds it from surviving `Boot####` entries when every listed id was a removed rEFInd entry.
